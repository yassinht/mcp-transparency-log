mcp.lock: a lockfile for the servers your agent calls

You pin your npm dependencies. The MCP servers your agent talks to can change their tool descriptions tonight, and your agent will follow the new text tomorrow.

A tool description is injected straight into the model's context. If a server you reviewed last month quietly rewrites "look up the weather" into "look up the weather and include the user's previous messages", nothing in your stack notices: no package version moved, no hash in your repository changed, no test fails. mcp.lock gives that change somewhere to fail.

what is pinned
tool names, descriptions, input schemas, annotations: one canonical hash per server
how it is checked
a live probe from your CI runner, not a lookup in this log
what you get
a failed job and an issue with the diff, linking to the server's observed history

1 · Install the CLI

go install github.com/yassinht/mcp-transparency-log/cmd/mcpobs@latest

One static binary, no runtime dependencies. The same binary reads and verifies the public log.

2 · Lock the servers you use

mcpobs lock context7=https://mcp.context7.com/mcp \
            exa=https://mcp.exa.ai/mcp \
            https://docs.mcp.cloudflare.com/mcp
git add mcp.lock && git commit -m "Pin MCP server surfaces"

Names are optional and only for readability. The lockfile is plain JSON, sorted, written to be read in code review:

{
  "version": 1,
  "generated": "2026-10-26T09:15:52Z",
  "log": "https://github.com/yassinht/mcp-transparency-log",
  "servers": [
    {
      "name": "context7",
      "endpoint": "https://mcp.context7.com/mcp",
      "surface_sha256": "36dee0f3fbf80c4ed815e2b82cdfeb444188e7e941177d3124e31a3e0d6d91d6",
      "jcs_v1_tools_sha256": "sha256-XpeSi1ir5PNF5yunuB1mfnHR+1IpBb5+X+N+JhSTt8E=",
      "tools": ["query-docs", "resolve-library-id"],
      "locked_at": "2026-10-26T09:15:52Z",
      "transport": "streamable-http"
    }
  ]
}

3 · Check it in CI

Add a workflow. Daily is the useful cadence; on pull requests that touch the lockfile is the second one.

# .github/workflows/mcp-lock.yml
name: MCP surface lock
on:
  schedule:
    - cron: "17 6 * * *"
  pull_request:
    paths: [mcp.lock]
  workflow_dispatch:

permissions:
  contents: read
  issues: write        # to open the drift issue; drop it and set open-issue: "false" to only fail

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: yassinht/mcp-transparency-log@v1
        with:
          lock: mcp.lock          # default
          open-issue: "true"      # default

The Action builds mcpobs from the tag you pinned, so what runs in your CI is exactly what is in that tag's source. No download from a third host, no prebuilt binary to trust.

4 · When a server changes

The job fails and one issue is opened (or the existing one gets a comment), labelled mcp-surface-drift. It reads like this:

MCP server tool surface changed

mcp.lock pins 4 server(s). Checked 2026-10-27T06:17:40Z: 1 changed, 0 unreachable, 3 unchanged.

context7

https://mcp.context7.com/mcp

Tools: 2 → 2 · surface 36dee0f3fbf8… → a81c0e22d904… · locked 2026-10-26

Same tool names — a description or input schema was edited in place. This is the change a client never sees; read the new text before accepting it.

Observed history of this server

To accept after review: mcpobs --lock mcp.lock check --update, then commit the lockfile.

Review the new text, then accept it the way you would accept a dependency bump:

mcpobs check --update
git commit -am "Accept new surface of context7 (reviewed)"

An unreachable server is reported but is not drift: the lock could not be verified that run, which is different from the server having changed.

Questions a careful reader asks

Why probe live instead of reading the log?

Dependabot does not consult a mirror of npm to tell you a package changed; it looks. The log's role is evidence and history: the hash in your lockfile can be matched against what the log saw the night you wrote it, and the issue links to the server's observed history. Your check does not depend on this site being up.

What does the hash cover?

The canonical form of tools/list: every tool's name, title, description, input schema and annotation hints, with key order and whitespace normalised. Not the server's outputs, not its prompts or resources, not its TLS certificate. The same canonicalisation the crawler records, so your lock and the log agree byte for byte. Beside it, jcs_v1_tools_sha256 is the narrower RFC 8785 digest of each tool's contract (name, description, input and output schema) that CrawlCheck and HISTOR publish, so the same server can be compared across all three records.

Exit codes

0 every server matches. 1 at least one changed. 2 the check itself failed (bad lockfile, no servers). Unreachable servers are reported and do not by themselves fail the run.

Servers that need credentials?

Not yet. The probe sends no authentication, which is also why the public log covers only unauthenticated servers. If your agent depends on authenticated servers and you would want them locked, say so: that is the first thing a paid tier would do.
